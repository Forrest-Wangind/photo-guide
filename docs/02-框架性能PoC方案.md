> 版本 v0.2 · 2026-10-14 · 状态：**框架已定案 KMP → 本 PoC 降级为可选的 GC 闸门 + 帧通路验证**
> 上游：`docs/00-总体框架与实施计划.md` §3.5 / §3.7 / §10.3
> 目的：原为把「Flutter vs Kotlin Multiplatform」从**争论**变成**测量**；**框架已定案 KMP 后**，本文件保留两处价值——
> ① **S5 的 GC 抖动闸门**（KMP 唯一未验证的硬问题，数小时即可跑）
> ② 若日后需要，**P-B 真机帧通路验证**可直接复用下面的工程定义与测量项

## 0. 这个 PoC 要回答什么

### 要证的

> **在"帧和推理全部关在 native"这个前提下，Flutter 与 KMP 的性能差距到底有多大？以及为拿到这个性能，两条路各自要付出多少 native 胶水代码？**

### 不要证的（明确排除）

- ❌ 谁是"更好的跨平台框架"（这是产品问题，不是性能问题）
- ❌ 谁的 UI 更好写、生态更全（PoC 里两边都不写复杂 UI）
- ❌ 模型精度、构图算法正确性（与本决策无关）

### 一个必须提前说清的前提

**纯推理速度两条路完全相同**——热循环都是同一个 NCNN + 同一个模型。差异只在两处：

1. **帧怎么到达 C++**（相机回调 → native 缓冲）
2. **结果怎么回到上层**（native → Dart / Kotlin → UI）

所以这个 PoC 本质是在测**语言边界的价格**，而不是在测模型。这也决定了：**凡是两条路共享的部分（shim、预处理、推理），都必须写成完全一样的代码**，否则测出来的差异没有意义。

### 1.2 三个约束，以及它们分别怎么处理

#### 约束 ①：iOS 测不了（没有 macOS）

PoC **只能覆盖 Android**。iOS 侧的性能（尤其 Kotlin/Native 的 GC 表现）**无法用本 PoC 实测**。

**处理方式（诚实标注，不掩盖）**：
- iOS 侧风险降级为「代码可行性审查 + 开源先例」，不产出性能数字
- 已有先例：`klover`（KMP，iOS 走 CoreML/Vision + AVCaptureSession）、`GalwayBus`（两侧相机代码都用 Kotlin 写）、Dynamsoft CMP 扫码器（`.def` cinterop 接 XCFramework）
- **在最终报告里，iOS 相关结论一律标注「未实测，来源为开源先例」**

#### 约束 ②：没有真机，只有模拟器

**模拟器数字不能用来做决策**：x86 架构、没有真 NPU/ISP、没有真实温升。用它测出的"帧率"是误导性的——**而误导性数字比没有数字更糟**。

**处理方式**：PoC 拆成三段，其中两段不依赖真机。

| 段 | 内容 | 需要真机？ | 能回答什么 |
|---|---|---|---|
| **P-A 离线基准** | PC 上跑预录视频，定速 30fps 灌入完整链路 | ❌ 不需要 | 预处理 + 推理 + 回传的分段耗时；**可重复、可回归** |
| **P-B 真机端到端** | 真实相机 → 分段耗时 + 掉帧率 + 10 分钟温升 + 内存 | ✅ **必须** | 帧通路真实表现、是否阻塞预览、热降频 |
| **P-C GC 抖动隔离** | PC 上用 Kotlin/Native (**mingwX64**) 编 benchmark，模拟热路径分配模式 | ❌ 不需要 | **Kotlin/Native GC 抖动是否存在**（§3.7.5 最大未知数） |

> **P-C 是这个方案里最巧的一步**：Kotlin/Native 的 GC 风险通常被认为"只有 iOS 上才能测"，但 Kotlin/Native 也支持 `mingwX64` / `linuxX64` —— **同一套运行时、同一个 GC 实现**。虽然不等价于 iOS，但足以回答"这个抖动存在吗、量级多大"这个**定性**问题。不需要 Mac，不需要手机。

#### 约束 ③：磁盘只剩 15~17 GB（两盘均 94% 满）

需要腾出 **8~10 GB**。粗算：

| 项 | 估算 |
|---|---|
| Flutter SDK | ~1.0 GB |
| Kotlin/Native konan 工具链 | ~1.5 GB |
| 两个 PoC 工程 + Gradle 构建产物 | ~1.5 GB |
| Gradle 依赖缓存增量（AGP / Compose / CameraX） | ~1.5 GB |
| Android 构建中间产物（NDK 编译 NCNN） | ~1.0 GB |
| 余量 | ~2 GB |

**这一项不做，PoC 跑不起来。**

## 2. 最小工程定义（两条路严格对称）

**MVP 只做一件事：相机 → native 检测 → 画框 + 耗时数字。**

### 2.1 必须包含

| # | 模块 | 要求 |
|---|---|---|
| 1 | 单页 App | Android only，相机页全屏 |
| 2 | 预览通路 | 相机预览 30fps，**零拷贝**（Flutter: Texture｜KMP: AndroidView + PreviewView） |
| 3 | 分析通路 | CameraX `ImageAnalysis`，`YUV_420_888`，目标 640×640，`STRATEGY_KEEP_ONLY_LATEST` |
| 4 | 预处理 | YUV→RGB + resize + 归一化 → 输入 tensor（**第一阶段允许 CPU 版，如实记录；GPU 版作为第二阶段**） |
| 5 | 推理 | **同一个 `yolo26n` NCNN 模型 + 同一个 C++ facade** |
| 6 | 回传 | 归一化 bbox 数组（`float[]`） |
| 7 | Overlay | 画方框（Flutter: CustomPainter｜KMP: Compose Canvas） |
| 8 | 性能浮层 | `cap / pre / det / post / bridge / draw / fps`，**每段独立打点** |

### 2.2 明确不做（防止 PoC 膨胀成项目）

❌ pose 关键点　❌ ByteTrack 跟踪　❌ 颜色提取　❌ 规则引擎　❌ LLM
❌ UI 美化　❌ 权限流程完善　❌ 生命周期健壮性　❌ 错误处理　❌ 多语言
❌ iOS（见约束①）

### 2.3 关键的对称性要求

**两条路的 native 代码必须写成同一份：**

```
native/
├── ncnn_facade.cpp        ← 同一份，extern "C" 接口（两条路都要写，dart:ffi 也只能调 C ABI）
├── preprocess.cpp         ← 同一份
├── yolo_postprocess.cpp   ← 同一份（decode + NMS，同时是 KMP 共享逻辑的取样）
└── CMakeLists.txt         ← 同一份
```

两侧差异**只在胶水层**：
- **Flutter**：Kotlin 侧持有帧 → 喂给 facade；`dart:ffi` 读结果；Dart 注册 Texture + 画框
- **KMP**：Kotlin 侧持有帧 → JNI 喂给 facade；Kotlin 直接读结果；Compose 画框

> 💡 **本 PoC 原本很可能揭示一件事**：两侧的 native 代码高度重合，Flutter 只是多了"注册 Texture + 从 Dart 读结果"这一层胶水。**这个预判在框架定案 KMP 后已不再需要验证**；但它的推论仍然成立——§3.6 估的"2~2.5 倍工作量"偏高。下面 §2 的 MVP-F 相关内容保留，仅作历史记录。

## 3. 测量项

| # | 指标 | 单位 | 怎么测 | 用途 |
|---|---|---|---|---|
| ① | 分析通路分段耗时 | ms (P50/P95) | native 打点 | **核心对照** |

| ③ | 检测帧率 | fps | 计数器 | 参考 |

## 4. 判定规则（预先注册）

**先写下规则，避免事后为已选的答案找理由。** 以下判定在跑之前生效、跑之后不许改。

| # | 情形 | 判定 |
|---|---|---|
| R1 | ② 两条路预览掉帧都 < 5%，且 ① 差值 ≤ 15% | **性能无实质差异** → 转由 ⑦⑧ 与生态决胜 → **倾向 Flutter**（生态厚、UI 强、已决策、C 盘已就绪） |
| R2 | ① Flutter 落后 > 25%，或 ② Flutter 掉帧 > 10% | **选 KMP** |
| R3 | ⑦ Flutter native 胶水量 ≤ KMP 的 1.3 倍 | 强化 R1 结论（额外成本很小） |
| R4 | ⑦ Flutter native 胶水量 > KMP 的 2 倍 | 强化"选 KMP" |
| R5 | ⑩ Kotlin/Native GC 抖动 P99 > 2 × P50 | **降权 KMP**（其最大卖点被自己抵消） |
| R6 | ② 两条路都不达标 | 说明"30fps"需按 §5.1 分层策略重谈，**扩大 PoC 范围**，不在两者间选 |
| R7 | ⑥ 两条路都在 5 分钟内掉 40%+ 帧率 | 触发产品级重估（不只影响选型） |

**R1 是最可能的结果**——因为热循环本来就相同。所以这个 PoC 真正的产出很可能是**两条数据线 + 一份开发成本对照**，而不是"谁快谁慢"。

## 7. 这个 PoC 测不到的（诚实清单）

| 测不到的东西 | 原因 | 影响 |
|---|---|---|
| iOS 侧真实性能 | 无 macOS | 选 KMP 时，iOS 是主要收益来源 → **风险不对称** |
| Kotlin/Native 在 iOS 上的 GC 表现 | 同上 | P-C 用 mingwX64 只能给**定性**结论 |
| 真 NPU 加速效果 | 第一阶段用 CPU 路径 | CPU 路径的差异结论**不能直接外推到 delegate 路径** |
| 长时间（>10 分钟）稳定性 | 时间盒限制 | 温升测试只覆盖 10 分钟 |
| GPU 预处理 shader 的收益 | 第二阶段才做 | 若第一阶段差异很大，第二阶段可能抹平大部分差异 |

> **最后一行很重要**：如果第一阶段测出 Flutter 落后，**必须先做完第二阶段的 GPU 预处理再下结论**——否则可能把一个"还没优化完"的中间状态误判成架构缺陷。

## 8. 下一步（KMP 定案后的更新）

### 8.0 ✅ 状态更新：框架已定案 KMP（2026-10-14）

用户已拍板改为 **Kotlin Multiplatform**。因此本 PoC 的定位发生变化：

- **不再需要"Flutter vs KMP 对照"**——对照的前提（框架未定）已消失。§2 的 MVP-F（Flutter 版）**作废**。
- 原 §4 判定规则 R1/R2/R3/R4 的"两者对比"部分失效；**只剩 R5（GC 抖动）仍然有效**，且它现在的作用不是"选框架"，而是**给 KMP 路线做风险早筛**。
- §2 的 MVP-K（KMP 版）与 §3 的测量项**保留**，可作为 M1 真机验证的现成脚手架。

### 8.1 ⭐ 推荐：只跑 S5 —— PC 上的 Kotlin/Native GC 抖动基准

**这是本文件现在唯一仍被推荐执行的部分。** 其余（S0/S1/S2/S6/S7）**不再作为开工前置**。

理由：KMP 路线唯一还没有答案的硬问题是 **Kotlin/Native GC 抖动**（主方案 §3.7.5-2）。而它**测试成本极低**：

| | 最大未知数 | 测它需要什么 | 成本 |
|---|---|---|---|
| Flutter | 自研相机帧通路能否达标 | 真机 + 完整 native 工程 | 已随 Flutter 出局而作废 |
| **KMP** | **Kotlin/Native GC 暂停** | **PC 上编 `mingwX64` benchmark** | **低（只需 S5）** |

**闸门判定（对 KMP 路线本身）**：

- ⑩ GC 抖动 **P99 < 2 × P50** → 风险面基本清空 → **放心推进 M1，热路径按 §3.8 纪律写**
- ⑩ GC 抖动 **P99 > 2 × P50** → 触发主方案 §8.2 备选路径：**把更多热逻辑下沉 C++**（而非换框架——框架已定案）
- 结果模糊（1~2 倍之间）→ 在 M1 实测中重点观察，并强化"预分配缓冲 + 对象池"纪律

**闸门成本：数小时。不需要腾磁盘（S5 只需 konan 工具链，约 1.5~2 GB）、不需要真机、不需要 Mac。**

> ⚠️ 与"开工"的关系：**S5 不再阻塞 M0**。但因为它便宜且能提前消除唯一未知数，**建议与 M0 并行做**。

### 8.2 真机帧通路验证（可选，M1/M1.5 阶段复用）

若要在 M1 真机上做一次"帧通路体检"，可直接复用本文件 §2.1 的 MVP-K 工程定义与 §3 的测量项（尤其 ② 预览掉帧率、⑥ 10 分钟温升曲线）。此时需要你给两件事：

- **S0 腾磁盘**（8~10 GB）
- **S1 插一台 Android 真机**（中端机优先——它才是性能下限）

**iOS 侧仍需一台 Mac 才能实测**（约束①）。
