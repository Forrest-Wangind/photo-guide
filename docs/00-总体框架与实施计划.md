### 0.2 主线技术结论（KMP 路线）

| 决策项        | 结论                                                                       | 一句话理由                                               |
| ---------- | ------------------------------------------------------------------------ | --------------------------------------------------- |
| 框架         | **KMP**：`commonMain` 共享逻辑，`androidMain`/`iosMain` 各自实现相机                 | 本 App UI 极简、逻辑层重——共享的正是最该共享的，且可单测；见 §3.7/§3.7.7     |
| 相机层        | expect/actual 共享接口；Android=CameraX，iOS=AVCaptureSession；**帧全程不进任何跨语言边界** | 相机线程可同步回调进 Kotlin（新内存模型），无需"实现通路"这个环节，见 §3.7.2      |
| 本地推理       | **自研 C++ 层（NCNN）**，经 JNI（Android）/ cinterop（iOS）暴露；前置 `extern "C"` shim  | 与任何跨平台方案共用同一份 C++ 源码；见 §3.8。**Phase 1 不需要，Phase 2 才用** |
| 本地模型       | **Phase 1：无**；Phase 2：**YOLO26n + YOLO26n-pose**（或 PicoDet-S/MoveNet，见 §4.7 与 03 文档） | 见 §2.2 与 `docs/03-本地模型选型横评.md`                       |
| 不用 RT-DETR | 否                                                                        | Transformer 解码算子移动端 delegate 支持差，易回退 CPU；精度优势对本场景无用 |
| 30fps 怎么实现 | **"检测 10~15fps + 跟踪补帧 30fps"，不是每帧都推理**                                   | 构图是慢变量；这是方案可行的唯一前提，见 §5.1                           |
| **流畅性基线**  | **按"帧时间的确定性"验收，不按平均值**（P99 ≤ 33.3ms、连续掉帧 ≤ 2 帧）                          | 见 §5.1.1——它把散落的架构决策串成一条主线                           |
| 中间层语言      | 跟踪/特征/规则引擎写 **Kotlin commonMain**                                        | 近原生速度 + 可单测 + 双端共享；不用像 Flutter 那样沉进 C++，见 §3.7.4    |
| Debug 轮廓   | Compose Canvas 叠加层                                                       | 见 §5.3                                              |
| 远端大模型输入    | **按形态区分**：Phase 1 单图默认传图；Phase 2 实时默认不传图（可用时传缩略图+裁剪图+JSON）                 | 见 §2.4 与 §6.1                                       |
| 降级策略       | 本地规则引擎兜底，LLM 挂了 App 仍然有用                                                 | 断网/超时不能变成"白屏"                                       |

**风险集中在三处**：① **Kotlin/Native GC 抖动**（流畅性头号风险，见 §5.1.1 与 §8.2）；② **iOS 侧无法在本机实测**（无 Mac，见 §8.2）；③ **Phase 1→Phase 2 的接口若未定死，会导致推倒重来**（见 §2.5）。

## 1. 产品定义

### 1.1 真实痛点拆解

"给女友拍照的无能为力感"其实由三个独立问题构成，混在一起才会导致情绪崩盘：

| 痛点         | 典型表现         | 本产品的解法                   |
| ---------- | ------------ | ------------------------ |
| **看不到问题**  | "我觉得挺好的啊"    | 本地模型把画面变成可量化的构图指标        |
| **不知道怎么办** | "再往左一点？"反复试错 | LLM 把指标翻译成具体动作指令         |
| **不敢指挥**   | 不知道怎么跟模特说    | 提示卡同时给「摄影师侧动作」+「模特侧口播台词」 |

第三条是**差异化点**。市面上构图辅助 App（OpenCamera、各类网格线工具）都只解决构图正确性，不解决"你得对她说点什么"。一个合格的提示应该是双栏的：

```
┌─────────────────────────────┐
│ 👤 你：后退一步，蹲下 30cm    │  ← 摄影师动作
│ 💬 对她说：「头往右转一点，    │  ← 直接照念
│     看远处，别看我」          │
└─────────────────────────────┘
```

### 1.2 用户意图的三档输入

| 档位         | 形态       | 示例                       | 本期   |
| ---------- | -------- | ------------------------ | ---- |
| **L0 默认**  | 预设场景按钮   | 人像 / 全身 / 半身 / 风景人像 / 自拍 | ✅ 必做 |
| **L1 文字**  | 一句话      | "突出她的红裙子"、"要能看见后面的海"     | ✅ 必做 |
| **L2 参考图** | 上传一张图学着拍 | "照这张的感觉拍"                | ⏳ 二期 |

### 1.3 什么算"成功"

不是"建议像专业摄影师"，而是**用户照做之后出片率提高**。所以评测指标要能落地：

- 构图规则命中率：主体眼睛落在上三分线 ±8% 内的帧占比
- 建议采纳率：提示出现后 2 秒内用户发生了对应动作的比例（用 IMU 或画面变化判断）
- 主观：可懂性 1-5 分、是否愿意再次使用
- **流畅性**：见 §5.1.1——"不卡"是体验的前提，不是加分项

## 2. 整体架构

四层。**核心设计原则：本地做所有实时的事，远端只做"翻译"。**

```
┌───────────────────────────────────────────────────────────────┐
│ L4 交互层  提示卡 / 引导箭头 / 取景框 / Debug Overlay          │
│            Compose（共享）+ 取景器双端原生 + Canvas 轮廓绘制     │
├───────────────────────────────────────────────────────────────┤
│ L3 决策层                                                     │
│   ┌── 本地规则引擎 ──────┐   ┌── 远端 LLM ──────────────┐      │
│   │ 构图评分/三角法/头空间 │   │ 特征 JSON + 意图 → 指令  │      │
│   │ <1ms，离线可用         │   │ 1.5~2.5s，需网络         │      │
│   │ Kotlin commonMain      │   │ Ktor + SSE（commonMain） │      │
│   └──────────────────────┘   └─────────────────────────┘      │
├───────────────────────────────────────────────────────────────┤
│ L2 感知层                                                     │
│   跟踪/特征/规则 → Kotlin commonMain（可单测）                  │
│   检测/pose/预处理/后处理 → native C++（NCNN）                  │
│   ★ 相机线程同步回调进 Kotlin；帧不进任何跨语言边界             │
├───────────────────────────────────────────────────────────────┤
│ L1 采集层   CameraX ImageAnalysis / AVCaptureVideoDataOutput   │
│            expect/actual 各自实现，帧流在平台语言内直取         │
└───────────────────────────────────────────────────────────────┘
```

> **注意**：上面的 L2 是 **Phase 2** 的完整形态。**Phase 1 的 L2 是空实现**（`PerceptionSource` 的 NoPerception 实现），用户拍的单张图直接上云（§2.5）。

### 2.1 分层职责与频率预算（关键表）

| 层     | 组件                                   | 目标频率                | 单次耗时预算    | 运行位置              |
| ----- | ------------------------------------ | ------------------- | --------- | ----------------- |
| L1    | 相机预览                                 | 30 fps              | —         | 平台原生预览视图          |
| L1    | 帧回调 + GPU resize/crop                | 30 fps              | ≤ 3 ms    | 相机线程              |
| L2    | YOLO26n 检测（640²）                     | 10~15 fps           | 40~70 ms  | NPU/GPU/CPU       |
| L2    | YOLO26n-pose 关键点                     | 10~15 fps           | 30~50 ms  | 同上                |
| L2    | ByteTrack 补帧                         | 30 fps              | ≤ 1 ms    | Kotlin commonMain |
| L2    | 几何 + 颜色特征                            | 30 fps              | ≤ 1 ms    | Kotlin commonMain |
| L2    | 深度采样                                 | 3~5 fps（每 6~10 帧）   | 见 §5.4    | 同上                |
| L2→L3 | **结果回传（Kotlin 直调 / JNI / cinterop）** | 30 fps              | ≤ 0.3 ms  | 数百 float，不是图像     |
| L3    | 本地规则引擎                               | 30 fps              | ≤ 1 ms    | Kotlin commonMain |
| L3    | 远端 LLM                               | 0.4~0.7 Hz          | 1.5~2.5 s | 云端                |
| L4    | Overlay 绘制（Canvas）                   | 30 fps              | ≤ 2 ms    | 平台 GPU            |

**中端机（骁龙 7 系 / A15）总预算约 85~130ms/帧用于 AI 链路 → 即 8~12 fps 检测。旗舰机 15~20 fps。这个数字是诚实预期，不是营销数字。**

> **这张表是 Phase 2 的预算。Phase 1 只有 L1（拍照）+ L3（云端 LLM）+ L4，没有 L2。**

### 2.2 本地模型的必要性（2026-10-14 追加论证）

> 用户提问：「使用本地模型处理图像是否有必要？」——这等于在质疑全案的基石。

#### 2.2.1 结论先行

**必要性的唯一来源是一件事：要不要 <300ms 的实时闭环。**

| 你的选择            | 本地模型 | 后果                                                                               |
| --------------- | ---- | -------------------------------------------------------------------------------- |
| **要实时闭环**（实时取景指导 / 实时叠加箭头） | **必要且不可替代** | 保持现方案形态                                                                          |
| **不要**（接受"拍照 → 等 1~2s → 出文字"） | **可整个砍掉** | 连带砍掉全案最危险的 **60~70% 工作量**：native 帧通路 / NCNN / cinterop / 量化 / GC 抖动 / AGPL 全部消失；M0+M1+M1.5 合并为一个里程碑 |

其他理由（成本、隐私、离线）**都比直觉弱得多**——见下。

#### 2.2.2 三档时间量级（这是本轮最硬的实测数据）

| 档位                       | 单次延迟                            | 可持续频率      | 能承担什么             |
| ------------------------ | ------------------------------- | ---------- | ----------------- |
| **端侧专用小模型**（YOLO26n / MoveNet / pose） | **20~70 ms**                    | **15~30 Hz** | 感知：位置 / 姿态 / 几何 / 跟踪 |
| **云端多模态大模型**（豆包 / 通义 VL）  | 端到端 **1~2 s**（TTFT 340~410ms）   | **0.5~1 Hz** | 理解：语义 / 场景 / 创意台词 |
| **端侧多模态小模型**（Qwen3-VL-2B） | **7.4 s**（TTFT 3.2s，峰值内存 2.27GB） | **0.13 Hz**  | **两头不占**          |

**三条被数据推翻的直觉：**

1. ❌ **「本地跑个小 VLM 替代云端」是死路。** Arm 官方在 vivo X300 上实测 Qwen3-VL-2B（Q4_K_M）：首 token **3239ms**、端到端 **7387ms**、峰值内存 **2.27GB**。**比调云端慢约 5 倍，模型还更弱。**（网传"骁龙 8 Gen3 上 15fps 视频流"与 Arm 官方实测差两个数量级，属营销口径。）
2. ❌ **成本不构成选本地的理由。** 通义 VL ¥0.0028/张、豆包 ¥0.003/张。按 1Hz 拍 10 分钟 ≈ 600 张 ≈ **¥1.8**。**纯自用下可忽略。**
3. ⭐ **平台 API 的性能被严重低估。** ML Kit Pose 在 **Pixel 3 XL（2018 年机型）**上就 ~30 FPS（33 关键点）；MoveNet 在手机上 **34~51 FPS**。且 ML Kit Pose 吃 `media.Image`，CameraX `ImageAnalysis` 给 `ImageProxy` → **native-to-native，天然符合"帧不进共享层"原则**。

#### 2.2.3 本地模型的正当理由（按强度排序）

| 理由            | 强度       | 说明                                       |
| ------------- | -------- | ---------------------------------------- |
| **实时闭环 <300ms** | ★★★★★ | 唯一不可替代的理由；云端 1~2s 达不到               |
| **实时叠加层**     | ★★★★☆   | 引导框 / 箭头 / 轮廓。**Phase 1 单图形态下做不了**（见 §2.3.3） |
| **离线 / 弱网可用** | ★★★☆☆   | 有真实价值但非核心                                |
| **隐私**        | ★★★☆☆   | "给女友拍照"是强隐私场景，但**可以靠"不上传"而非"本地推理"解决**     |

#### 2.2.4 砍掉它能省什么（最大的诱惑）

- §3.5 / §3.7.5 整条 native 相机帧通路 → 不需要
- NCNN + cinterop/JNI + C++ 推理层 + INT8 量化 + 模型导出链路 → 不需要
- Kotlin/Native GC 抖动风险、AGPL 风险 → 都不存在
- → **M0 / M1 / M1.5 三个里程碑合并成一个**，全案最危险的那 60~70% 工作量消失

#### 2.2.5 代价

建议节奏掉到 **1Hz**（受云端 TTFT 限制）、**实时叠加层做不了**、**无网时完全失效**。

#### 2.2.6 三条路线

| 路线                            | 本地角色                                                   | 相对工期               | 适用与注意                                                              |
| ----------------------------- | ------------------------------------------------------ | ------------------ | ------------------------------------------------------------------ |
| **A. 云端直连**                   | 无                                                      | 最短（≈ C 的 **1/3**）  | v1 只做文字提示，快速验证产品                                                   |
| **B. 平台 API 感知 + 云 VLM**      | ML Kit 姿态 / 人脸网格 / 主体分割 / 目标检测 · Apple Vision        | 中                  | ★ 评审推荐（Phase 2）。遗留风险：姿态检测官方仍标 **beta（无 SLA）**；iOS 侧支持面需逐 API 核实 |
| **C. 自研 YOLO26n + NCNN**      | 全自研（可含运行时动态模型）                                         | 最长                 | 需要自定义目标类别 / 多人体 / 极致可控；详见 §4 与 `docs/03-本地模型选型横评.md`           |

> 📌 **事实修正注（2026-10-14）**：用户决定「**国内不能使用 ML Kit，直接放弃**」。需要留档的是：**这个技术判断不成立**——ML Kit 的 **bundled 版**把模型静态链接进 App、**纯端侧离线运行、不联网、不依赖 GMS**；而本方案要用的**姿态检测 / 人像分割 / 主体分割官方只提供 bundled 变体，根本没有 thin 版**（`com.google.mlkit:pose-detection`，无对应 `play-services-mlkit-*`）。**国内无 Google Play 服务的机型可以正常使用。**
>
> 但如果是出于"**不想在产品里引入 Google 生态依赖**"的商业考虑而放弃，那是完全合理的判断。**已尊重该决定**：路线 B 的本地角色改为国产替代 **MoveNet**（纯 TFLite、无 GMS 依赖、双端可共享一份推理代码）。

### 2.3 感知层与大模型的接口形态（2026-10-14 追加）

> 用户追问：「把 YOLO 解析出的文本（box/conf/cls）给到大模型，是不是更有助于分析、起码能节省解析时间？」

#### 2.3.1 先澄清一个前提：YOLO 是「图像 → 数字」的翻译器，不是「图像 → 小图」的压缩器

用户的心智模型是「原图 → YOLO → 精简图 → 大模型」。**实际链路不是这样**：

```
原图 ──> YOLO ──> box:[0.31,0.22,0.68,0.96]
                   cls: person
                   conf: 0.91
                   kpts: [17 个坐标]
                   color: #B3243A
                  ↑↑↑ 全是数字，之后没有"图"了 ↑↑↑
```

**所以"用 YOLO 把图预处理成小图再喂给大模型"这个设想，不是 YOLO 做得不好，是它压根不产出那种东西——第一步就断了。**

#### 2.3.2 喂给大模型的三条路

|                      | ① 直传原图    | ② 传标注图          | ③ 传 JSON（旧方案 §6.1） |
| -------------------- | --------- | --------------- | ------------------ |
| YOLO 的角色             | 不需要       | 在图上画框           | 出数字文本              |
| 上传体积                 | ~150KB    | ~150KB          | 几 KB               |
| 延迟                   | 1~2s      | 1~2s + 40ms     | ≈1s                |
| **大模型看到**            | **画面本身**  | 画面 + 注意力引导      | **只有数字**           |
| 能力                   | **真懂审美**  | 更准，但仍需传图        | **只能"算"，不能"看"**    |
| ⭐ **关键判断**           | 要"理解构图（审美）"就必须让模型看到画面 | — | JSON 给不了审美 |

#### 2.3.3 ⭐「前期只做单张图」直接推翻选本地方案的两个理由

用户明确「当前前期可以只考虑单张图片」。这**废掉了原本给本地模型的两个理由**：

| 用户给的理由        | 单图形态下是否成立                                                |
| ------------- | -------------------------------------------------------- |
| **防止视频流过载**   | ❌ **不成立**。单图没有"流"。防过载的正确手段是**抽帧 / 节流 / 变化触发**（§6.3），不是靠 YOLO 压缩 |
| **防止传图网络延迟**  | ⚠️ **大幅减弱**。单张 720p ≈150KB，4G 上传 0.2~0.5s、5G 几十毫秒，**且只传一次**，不是每秒一次 |
| （隐含）实时闭环 <300ms | ❌ **不成立**。"拍一张 → 分析 → 出建议"，1~2s 完全可接受                   |

→ **结论：单图形态下 YOLO 必要性大幅下降，最短路径 = 路线 A（单图直传云端 VLM）。**

#### 2.3.4 剩余价值（都可后加）

YOLO 在单图下只剩两项价值：

1. **定量几何**：云端 VLM 量不准像素级位置，"往左 5%""再近 30cm"这类指令只有本地量测给得出
2. **离线 / 隐私**

**两项都可以后加**：先用路线 A 跑通产品价值，之后再把本地模型作为"定量建议增强"插进来。**这样前期可以完全绕开 §4 与 §8.2 的全部 native 风险。**

### 2.4 给大模型喂什么：三件套（2026-10-14 追加，含实证）

#### 2.4.1 先纠正「节省解析时间」这个说法

**现代多模态大模型是统一 Transformer**——图像被 tokenize 成与文本**同一条 token 流**，**没有独立的"视觉处理管线"，也不存在"视觉税"**。延迟 ∝ **总 token 数**。

所以大模型看图不是在"解析"，**不存在"解析这一步"可以省**。真正该算的是 **token 账**：

| 输入形态          | 大致 token 数     |
| ------------- | -------------- |
| 原图 1024²     | **765~1400**   |
| 缩略图 512px    | **200~300**    |
| 精简 JSON（本方案）  | **30~80**      |

**但用户的核心直觉是对的**——减少喂进去的视觉内容、把注意力引到主体上，确实同时提升准确率与速度。有直接实证：

#### 2.4.2 ⭐ 一条直接验证该直觉的论文

> **《Bounding Boxes to Improve Small Language Model Performance on Vision-Based Grading Tasks》**（McGinness, 2026）
> 8 个开源 VLM（4B~72B）、126 份手写试卷，把**整页图换成 bbox 裁剪区域**：
>
> - 准确率 **0.728 → 0.840**（**+11.2 点，8 个模型全部提升**）
> - 输入 token **1463 → 679**（减半）
> - FLOPs **41T → 17T**

机制：去掉视觉干扰 + 图块变少 → 视觉 token 变少。

⚠️ **但形式要改**：论文验证的是「给**裁剪出来的图**」，**不是**「给 bbox 数字坐标」。而且**大模型的空间推理本身就不准**（"左右上下"经常搞混），指望它从 `[0.31,0.22,...]` 推出构图问题风险很高。

另有 **CropVLM** 证实「整图 + 裁剪」双输入最佳；**ENCORE**（华为）在 2B VLM 上 +1.43%。

#### 2.4.3 三件套

| 给什么                   | 管什么           |
| --------------------- | ------------- |
| ① **缩略图 512px**       | 全局场景与审美       |
| ② **主体裁剪图**（由检测框裁出）   | 局部细节 + 降 token |
| ③ **精简 JSON**（几何/颜色/姿态） | 像素级定量锚点       |

> **图给审美，裁剪给细节，JSON 给定量 —— 三者互补，不是替代。**

#### 2.4.4 对 §6.1「默认不传图」的修订

§6.1 选"默认不传图"成立的前提是**实时取景、每秒都要决策，传图太贵太慢**。

**它不是错，但它是取舍，不是更优解。**

- **实时形态（Phase 2）**：保留"默认不传图"，避免每秒上传拖垮延迟与成本
- **单图形态（Phase 1）**：**默认改为传图**（缩略图 + 裁剪图 + JSON）。否则"让大模型理解构图"这个目的拿不到

### 2.5 演进架构：Phase 1 单图 → Phase 2 30fps（✅ 已确认）

用户强调必须考虑"后期 30fps 视频流"——**架构上不能二选一，而是「接口先定，实现后填」**。

| 阶段             | 流水线                                                                     | 感知层                                  |
| -------------- | ---------------------------------------------------------------------- | ------------------------------------ |
| **Phase 1 单图** | 拍摄（单张照片） → 云端 VLM → 建议卡                                                | **空实现**（`NoPerception`）               |
| **Phase 2 30fps** | 相机流 → 感知层 → 跟踪 → 本地规则 → **即时提示**（<300ms）　∥　云端 0.5Hz → **深度建议** | YOLO26n / MoveNet（或平台 API）           |

**两条建议链路在 Phase 2 是并存的：**

- **本地链路**：出"快提示"（<300ms，箭头 / 框 / 短句）
- **云端链路**：出"慢建议"（0.5Hz，文案 / 台词 / 理由）

这正好落在 §5.1 那句「检测 10~15fps + 跟踪补帧 30fps + LLM 0.5Hz」上。

**⚠️ 硬纪律：`PerceptionSource` 接口在 Phase 1 就必须定义在 `commonMain`。**

```kotlin
// commonMain —— Phase 1 就定死，Phase 2 只换实现，上层一行不改
interface PerceptionSource {
    fun start()
    fun stop()
    /** 最新一帧的分析结果；Phase 1 恒为 null */
    val latest: StateFlow<PerceptionFrame?>
}

// Phase 1: class NoPerception : PerceptionSource   // 全空实现
// Phase 2: class YoloNcnnPerception : PerceptionSource
```

**这就是"避免前期图快、后期推倒重来"这个最常见架构陷阱的方法。** 上层（UI / 决策层 / LLM 客户端）从第一天起就面向接口编写，Phase 2 只替换实现。

### 3.5 ⚠️ Flutter 相机帧通路（已归档 —— 曾是核心技术风险，KMP 路线下不适用）

> 📌 **归档说明**：本节是 Flutter 路线独有的风险分析，**KMP 路线下不存在"自研相机帧 FFI 通道"这个环节**（见 §3.7.2）。保留作为决策留痕——它解释了"帧永进 Dart，只把结果给 Dart"这条设计原则的来源，也解释了为什么 Flutter 最终排到第三。

**问题本质**：Flutter 没有官方级的"逐帧原生处理器"。默认写法 `camera` 插件 + `startImageStream()` 会把每一帧 YUV 数据经 Platform Channel 拷进 Dart，30fps 下这是每秒 30 次跨语言拷贝（1080p YUV420 约 3MB/帧 → **约 90MB/s 的无谓搬运**），必然会掉帧和抖动。

> 📌 **2026-10-14 补充**：社区已出现第三方包 `flutter_native_vision_camera`（**v0.0.6**），提供"Dart 主 isolate 帧回调 + **native C/C++ 同线程同步钩子**"的类 VisionCamera 模型。但它版本极早、无生产验证，只能列为**观察项**，不能作为地基。

**解决方案（Flutter 路线）：帧永进 Dart，只把结果给 Dart。**

```
┌─ native (Kotlin / Swift + C++) ─────────────────────────────┐
│                                                             │
│  CameraX / AVCaptureSession                                 │
│        │                                                    │
│        ├──> [预览通路] SurfaceTexture ──> Flutter Texture ──┼──> Dart 只负责显示
│        │                                    (零拷贝，30fps)  │
│        │                                                    │
│        └──> [分析通路] YUV Image ──> GPU shader (resize/    │
│                                       crop/归一化)           │
│                              │                              │
│                              v                              │
│                    InferenceEngine (TFLite/NCNN)            │
│                              │                              │
│                    ByteTrack + 特征提取                      │
│                              │                              │
│                              v                              │
│                    结果结构体: {boxes[], kpts[], colors[],   │
│                                timings{}, fps}               │
└──────────────────────────────┼──────────────────────────────┘
                               │  dart:ffi（每次约 200~400 个 float，<0.3ms）
                               v
                        Dart 层：规则引擎 → LLM → UI
```

**四条硬性设计要求（KMP 路线同样适用 2/3/4 条）：**

1. **只在 native 侧持有帧内存**：Dart 侧任何接口都不接收图像字节，只接收结构化结果。这是能否达到 30fps 的分水岭。
2. **预览与分析走两条独立通路**：分析通路在自己的线程上跑，与预览互不阻塞。**分析线程卡住时预览必须仍然丝滑。**
3. **降采样在 GPU 上做**：不要把 1080p 帧拷到 CPU 再 resize。用 shader 一步完成 `crop → resize 到 640×640 → YUV→RGB → 归一化 → 写入推理输入 tensor`。
4. **所有耗时打点从 native 侧上报**：`capture / preprocess / inference / postprocess / track` 各段分别计时，随结果一起回传，直接喂给 Debug 浮层。**没有这个，性能问题无法定位。**

**已知坑（Flutter 路线，留档）：**

| 坑                                | 说明                           | 对策                                                             |
| -------------------------------- | ---------------------------- | -------------------------------------------------------------- |
| Android 部分机型不支持"预览/录像 + 图像分析"并行  | CameraX 能力查询可判定              | 启动时探测并行能力，不支持则降级为"仅拍照后分析"                                      |
| YUV 格式跨厂商不一致                     | `nv21` / `yuv_420_888` 语义有差异 | 用 `OUTPUT_IMAGE_FORMAT_YUV_420_888`，在 C++ 侧统一处理 stride/padding |
| iOS 版本方向与旋转                      | 帧方向 ≠ 屏幕方向                   | native 侧统一输出"已按设备方向校正"的帧                                       |
| Flutter Texture 与 CameraX 生命周期冲突 | 相机重开时纹理失效黑屏                  | 用 `TextureRegistry.SurfaceProducer`（新版 API）                    |
| iOS 后台/来电中断                      | AVCaptureSession 需要重建        | 监听 `AVCaptureSessionWasInterrupted`，恢复后重建                      |

### 3.6 相比 RN 方案，多出来的工作量（诚实清单，Flutter 路线留档）

| 项                          | 额外成本                       | 说明                                    |
| -------------------------- | -------------------------- | ------------------------------------- |
| 自研相机帧插件（Android + iOS 各一套） | **主要成本**                   | 约等于 RN 方案里 VisionCamera 帮你做掉的那部分      |
| native C++ 推理封装 + FFI 绑定   | 中                          | RN 侧 fast-tflite 直接可用；Flutter 侧要自己包一层 |
| GPU shader 预处理             | 中                          | RN 侧有 `vision-camera-resize-plugin`   |
| Overlay 坐标变换（预览 vs 帧坐标系）   | 小                          | 但调试起来烦人，建议 M1 就做坐标可视化                 |
| **总计**                     | **M1 工期约为 RN 方案的 2~2.5 倍** | 换来的是 UI 一致性、桌面/Pi 拓展性、DevTools        |

> ⚠️ **上表"2~2.5 倍"这个估值后来被修正，见 §3.7.5 第 1 条**——其中"native C++ 推理封装 + FFI 绑定"并非 Flutter 独有（KMP、RN 的 native plugin 同样需要 C ABI facade），额外成本主要在相机插件本身。

### 3.7 ★ Kotlin Multiplatform 复评（2026-10-14 追加）

> **触发**：用户追加约束「**性能是最重要的**」，确认"帧和推理都关在 native/C++ 里"的思路正确，并要求对比 KMP（理由：据说它能直接调 native 方法）。

#### 3.7.1 结论先行

**最终排序：KMP ＞ RN ＞ Flutter**（RN 的位置在同日追加的 §3.7.7 中被上调；KMP 经用户拍板定案）

必须诚实标注：**排序差距不在帧率上限**——三者热循环都是同一个 C++/NCNN，都能打到设备极限。**差距在「你被迫写多少 C++」和「迭代速度」。**

#### 3.7.2 为什么 KMP 在架构上更贴合

| 侧       | 机制                                                                                                                            |
| ------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Android | Kotlin/JVM 就是普通 Android 运行时。CameraX 的 `ImageAnalysis.Analyzer` **本质上是个 Kotlin lambda**，跑在专用 Executor 上，零跨语言动作                 |
| iOS     | Kotlin/Native 经 LLVM 编成真机码链进 app 二进制；cinterop 直接消费 AVFoundation / CoreML 头文件                                                  |
| **关键**  | Kotlin/Native 新内存模型（1.7.20 起默认，1.9.20 移除旧模型）**解除线程间对象共享限制**——官方原话"对象通过 interop 传递时不需要冻结，可以被任意线程访问和修改" → **相机线程可同步回调进 Kotlin** |

**对照**：Dart 有 `NativeCallable`，但 `isolateLocal` 限同线程、`listener` 是异步，而相机帧来自 native 自己的队列线程 → **拿不到「native 线程同步进入 Dart」这个效果**。这是**架构选择，不是能力缺陷**——Kotlin/Native 恰好选了相反的方向。

#### 3.7.3 ⭐ 决定性现实证据：klover（开源 KMP 应用）

已有开源项目在做与本项目**几乎同构**的事，这比任何 benchmark 都有说服力：

- 首页 = 实时预览 + 检测框 + 置信度 chip + **fps 计数器**（≈ 我们的 Debug 模式）
- **每帧端侧推理**：Android = ONNX Runtime + CameraX（**约 10 fps**，与 §2.1 的 8~12fps 预算吻合）；iOS = CoreML/Vision + AVCaptureSession
- **YOLO 后处理（decode + NMS）放在 `commonMain` 共享并单测** ← 证明"中间层用 Kotlin 写"可行
- 技术栈：KMP + Compose MP 1.11 + Kotlin 2.4 + AGP 9

同类参考：`GalwayBus`（两侧相机代码都用 Kotlin 写）、Dynamsoft CMP 扫码器（`.def` cinterop 接 XCFramework）。

#### 3.7.4 真正的决定性理由（不是帧率）

Flutter 路线下，**颜色直方图、mask 后处理、IoU 匹配、关键点平滑**这些要反复调参的代码，因为都在每帧路径上，**全得沉进 C++**（改一次编译一次、难单测）。
KMP 里这些用 Kotlin 写：**近原生速度 + 可单测 + 热迭代**。这才是 §3.6 那笔"额外工作量"真正的构成。

#### 3.7.5 ⚠️ 必须提前算进去的四个坑

1. **cinterop 只吃 C 头文件，不吃 C++ 类** → NCNN 的 `ncnn::Net` / `ncnn::Mat` 是 C++ 类，**必须写一层 `extern "C"` 薄 shim**（同类先例：在 Kotlin/Native 里接 Jolt 物理引擎）。**必须列进 M1。**
   > ⚠️ **但这并非 KMP 特有代价**：`dart:ffi` 与 RN 的 native plugin 同样只能调 C ABI，三者的 C++ 推理层需要**同一份** facade。这属于任何 C++ 推理层的共享成本，不构成选型差异。**推论：§3.6 估的"Flutter 多 2~2.5 倍"偏高**，额外成本主要是相机插件本身，不是推理集成。
2. ⚠️ **GC 暂停。** Kotlin/Native 用并发标记清除，官方场景建议里明确把"实时数据处理"列为需留意项。对策：推理/跟踪热路径全用**预分配缓冲 + 对象池**。**这是 KMP 路线最大的未知数，也是唯一可能抵消其架构优势的因素。**
   > 📌 **2026-10-14 追加**：用户把诉求明确为**"流畅性"**后（见 §5.1.1），这一项的定位**从"可选闸门"升级为"流畅性头号风险"**——因为 GC 停顿恰好落在每帧热路径上，是唯一能穿透"检测降频+跟踪补帧"这道保险的抖动源。
3. **Kotlin/Native 编译慢**，iOS 侧尤其，会影响迭代节奏。
4. **取景器属于"英雄界面"。** Compose MP 在 iOS 上虽已 Stable，但真实案例中有"高频渲染 + Metal/CoreAnimation 强耦合的组件共享后掉 15% 帧率"的教训，我们的取景器正好是这类。
   → **本方案采用"务实路径"：共享全部逻辑 + 相机层，取景器 UI 双端各自原生实现**（Android Compose / iOS SwiftUI + interop 内嵌视图）。

#### 3.7.6 状态

**✅ 已采纳（2026-10-14）。** 用户拍板框架改为 KMP，本复评结论正式生效。
剩余唯一未验项是 **Kotlin/Native GC 抖动**（§3.7.5-2），**已升级为流畅性头号风险**（§5.1.1），建议在 PC 上用 `mingwX64` 廉价闸门先测（见 §10.3）。

#### 3.7.7 ★ RN vs KMP：直接对比（2026-10-14 同日追加）

**先摆一个对 RN 有利、并推翻了我此前措辞的硬数据。**

VisionCamera 官方 benchmark（MLKit Vision Image Labeling，4K 帧）：

| 实现方式                                                   | 平均单帧耗时    |
| ------------------------------------------------------ | --------- |
| **纯原生**（Objective-C，完全不与 React 交互）                     | **68 ms** |
| **作为 Frame Processor Plugin**（Objective-C，经 JS 帧处理器调用） | **69 ms** |

**RN 的帧处理器插件只比纯原生实现慢约 1 ms。** 所以"RN 帧通路慢"**不成立**——它的帧通路几乎就是原生速度。这点必须先承认。

**那 RN 的问题在哪？在下一层。**

帧拿到之后，"每帧都要跑"的那批逻辑（预处理 / 跟踪 / 特征 / 调参）放哪？VisionCamera 文档写得很直白：

> "Since JavaScript is slower than native languages, it is recommended to use **native Frame Processor Plugins for heavy processing**."

于是只有三条路：

| 放法              | 代价                                                 |
| --------------- | -------------------------------------------------- |
| ① 留在 JS worklet | 慢，且**与相机回调同步 → 堵住相机线程**                            |
| ② 写平台原生插件       | **Android 写 Kotlin、iOS 写 Swift/ObjC —— 两套语言各维护一份** |
| ③ 写成共享 C++      | 可行，但等于放弃 RN 的语言优势，还要自己管 CMake/NDK                  |

**而本 App 恰恰每帧都是重活**，且这层逻辑（ByteTrack、颜色直方图、IoU 匹配、关键点平滑）是**要反复调参**的。

**决定性的一条（本 App 特有）**：

> 本 App 的 **UI 极简**（取景器 + 双栏提示卡），**逻辑层很重**（感知后处理 + 跟踪 + 特征 + 规则引擎 + LLM 编排）。
> **RN 共享的正是你最不需要共享的（UI）；KMP 共享的正是你最需要共享的（逻辑），而且 KMP 的共享逻辑可以直接单元测试。**
> 先例 `klover`：YOLO 的 decode + NMS 就放在 `commonMain` 并带单测。

**逐项对比：**

| 维度              | React Native                                | Kotlin Multiplatform             | 谁赢      |
| --------------- | ------------------------------------------- | -------------------------------- | ------- |
| 首版跑通速度          | VisionCamera + 社区插件，**最快**                  | 相机层要自己写（但只是 Kotlin 类）            | **RN**  |
| 相机层工作量          | **零**                                       | 每平台约一个类（有 klover / GalwayBus 先例） | RN      |
| 帧通路开销           | 插件 **~1ms**（实测）                             | 无中间层，理论更低                        | 打平      |
| **每帧逻辑的归属语言** ⭐ | JS worklet（慢）／平台原生（**Kotlin+Swift 两套**）／C++ | **Kotlin，双端共享 + 可单测**            | **KMP** |
| 逻辑单元测试          | 共享逻辑散在两侧，难测                                 | commonMain 直接测                   | **KMP** |
| 推理层             | `fast-tflite` 或 JSI C++ 接 NCNN              | 同一份 C++ facade + JNI/cinterop    | 打平      |
| 帧率上限            | 相同                                          | 相同                               | 打平      |
| UI 共享           | ✅ 全套                                        | Compose MP（取景器建议双端原生）            | RN      |
| 生态 / 第三方库       | **最丰富**（npm）                                | 较薄但生产可用                          | **RN**  |
| 迭代速度            | Metro HMR **最快**                            | Gradle / Kotlin-Native 最慢        | **RN**  |
| 语言总数            | JS + Kotlin + Swift + C++（4）                | **Kotlin + C++（2）**              | **KMP** |
| 热路径 GC          | Hermes GC（worklet 侧）                        | Android=ART；iOS=Kotlin/Native ⚠️ | RN 略优   |
| 成熟度风险           | VisionCamera 是社区项目，**v2→v3→v4 破坏性变更频繁**     | 工具链年轻；iOS 需 Mac                  | 各有      |

##### ⚡ 排名修正

**原排序「KMP ＞ Flutter ＞ RN」→ 修正为「KMP ＞ RN ＞ Flutter」。**

修正理由：此前把 RN 排最后，隐含假设是"RN 的 worklet 层是性能陷阱"。**官方 benchmark（~1ms 开销）证伪了它**——RN 的帧通路本身没问题，问题只在"每帧逻辑放哪"，而那是**开发成本问题，不是性能问题**。相比之下 Flutter 的帧通路**至今没有官方等价物**，是被迫从零造地基。

**RN 与 KMP 之间没有明显赢家**，取决于你更怕哪一件事：

- 怕**"调参要反复改两套平台原生代码"** → **KMP**
- 怕**"从零写相机层踩坑"** → **RN**

**→ 用户最终选择了 KMP**（更怕前者；且本 App 恰好是"逻辑重、UI 轻"的形态，正落在 KMP 的强项上）。

## 4. 本地模型方案

> ⚠️ **生效范围**：本章描述的是 **Phase 2** 的感知层方案（对应 §2.2.6 路线 C）。
> **Phase 1（单图形态）不需要本章的任何内容**——单张图直接上云（§2.5）。
> 完整选型横评见 **`docs/03-本地模型选型横评.md`**（检测 / 姿态 / 推理后端三张表 + 分阶段组合推荐）。

### 4.1 先澄清一个常见误解

你说"用 YOLO26n、RT-DETR 识别图像（包括物体的大小、位置、层次、颜色）"——**检测模型只输出「框 + 类别 + 置信度」**。其余四项必须二次加工：

| 你要的信息        | 真实来源            | 实现方式                                                       | 成本              |
| ------------ | --------------- | ---------------------------------------------------------- | --------------- |
| **大小**       | bbox 推导         | `面积占比 = boxArea / frameArea`；人像另算 `身高占画面比 = boxH / frameH` | ~0              |
| **位置**       | bbox 推导         | 中心点归一化坐标；到三分线/中心线的像素距离；头顶留白比例                              | ~0              |
| **层次（前后遮挡）** | ⚠️ bbox **给不了** | 方案 A：`脚底 y 坐标`排序（无倾角时的粗略深度）<br />方案 B：YOLO26n-depth 单目深度   | A ~0 / B 见 §5.4 |
| **颜色**       | crop 后处理        | 主体区域内 HSV 直方图 + k-means 主色；输出「主体色 / 背景主色 / 色相差值」           | ~1ms            |

**"层次"这项必须显式设计**，否则"背景抢主体"这类最关键的建议根本给不出来。

### 4.2 模型选型：为什么 YOLO26n 而不是 RT-DETR

| 指标            | YOLO26n                                                           | RT-DETR (r18 级)                                        | 备注                               |
| ------------- | ----------------------------------------------------------------- | ------------------------------------------------------ | -------------------------------- |
| COCO mAP50-95 | 40.9（e2e 模式 ≈40.3）                                                | r18 约 43（需实测口径）                                        | RT-DETR 精度略高                     |
| 参数量           | 2.4 M                                                             | ~20 M                                                  | **差 8 倍**                        |
| FLOPs         | 5.4 B                                                             | ~60 B                                                  | 移动端算力是硬约束                        |
| CPU ONNX 延迟   | 38.9 ms                                                           | 无公开移动 CPU 数据                                           | YOLO26n 比 YOLO11n(56.1ms) 快约 31% |
| T4 TensorRT   | 1.7 ms                                                            | —                                                      | 云端无意义差距                          |
| **架构可部署性**    | NMS-free + 移除 DFL → **计算图无自定义算子**，INT8 量化后 mAP 几乎不掉，delegate 映射干净 | 多查询 Transformer 解码器，移动端 delegate 覆盖差，易**静默回退 CPU**     | ⭐ 决定性差异                          |
| 移动端实测         | Ultralytics 官方文档明确支持 LiteRT / NCNN / CoreML                       | 社区口径"r18 在骁龙 8 Gen2 上 NNAPI 约 25fps"，**来源为技术博客，未交叉验证** | 需实测                              |

**判断：本场景不需要 55 mAP，需要的是「人在哪、多大、朝哪、和背景什么关系」。YOLO26n 精度够用，部署性完胜。RT-DETR 作为备选保留，等 M1 阶段做一次横评再定。**

> 📌 **补充（见 03 文档）**：YOLO26n **不是"性能最好"的，是"最省事"的**。它赢在一族通吃 + NMS-free + INT8 损失 <1%，**不赢在参数量**——PicoDet-S 只有它的 41%、NanoDet-Plus 49%，且都是 Apache-2.0。本场景只需 3~5 类，小模型可能更合适。**最终组合建议见 03 文档 §6。**

### 4.3 真正该微调的地方

YOLO26n 的 COCO 80 类里，**没有"人脸朝向""头肩关系""构图元素（天空/海/树/建筑）"这些本 App 最需要的类别**。所以 M1 之后建议做一次小规模微调：

- 目标类：`person`、`face`、`sky`、`water`、`tree/foliage`、`building`、`railing/ground-line`、`horizon`
- 数据：公开人像数据集（如 COCO person 子集 + 自采 200~500 张）+ 半自动标注（用 SAM 辅助）
- 规模：**YOLO26n 微调 1~2 万张图即可收敛**，成本可控

**M1 阶段先用官方权重跑通链路，微调放到 M4 之后。**

### 4.4 导出链路（KMP 路线下 NCNN 仍是主路径）

```
yolo26n.pt ──export(format="ncnn")─────> ncnn 参数 + bin    ← ★ 主路径（与共享 C++ 层天然适配）
     ├──export(format="tflite", int8)─> yolo26n_int8.tflite ← 备选
     └──export(format="onnx")─────────> onnx → tflite / ort  ← 保底
```

**为什么 NCNN 是主路径：** 无论是 KMP 还是 Flutter，推理层都是自研 C++，而 NCNN 是纯 C++、无 Python 依赖、ARM CPU 优化极好、Ultralytics 原生支持导出。KMP 侧经 `extern "C"` shim + cinterop（iOS）/ JNI（Android）接入，**与 Flutter 路线共用同一份 C++ 源码**——这也是 §3.7.5-1 那条"三方案共享 C++ 成本"的体现。TFLite 的优势（CoreML/GPU delegate、现成轮子）在自研 C++ 层里用不上。

> ⚠️ **待实测两项**：
>
> 1. Ultralytics 官方文档列出 YOLO26 支持 TFLite/LiteRT 导出，但社区实践中有"官方未直接支持 `.tflite`，需走 ONNX→SavedModel→TFLite"的说法（来源为博客，说法可能过时）。**以实测为准，两条路都留。**
> 2. YOLO26 的 NCNN 导出是否包含 NMS-free 的 end-to-end 输出图，以及输出张量布局。这决定 C++ 侧后处理要写多少代码。
>
> PTQ/INT8 需要校准集，**校准质量直接决定精度损失**——校准集请用人像场景（逆光、暖光、夜景各若干张），不要用纯 COCO 通用集。

## 5. 关键工程设计

### 5.1 "30fps" 到底怎么实现（本方案最重要的判断）

**如果按字面理解——每帧都跑 640×640 检测达到 30fps——在手机上做不到**（需要 <33ms 含前后处理，中端机 CPU 上 YOLO26n 单次就是 39ms，还没算 resize、后处理、Overlay 绘制）。

正确做法是**把"帧率"和"建议频率"解耦**：

```
相机预览    ████████████████████████████████  30 fps  （用户看到的画面，永远丝滑）
检测推理    ████        ████        ████      10 fps  （每 3 帧跑一次）
跟踪补帧      ██████████████████████████████  30 fps  （ByteTrack/光流，<1ms）
几何特征      ██████████████████████████████  30 fps  （纯数值计算，<1ms）
Overlay     ████████████████████████████████  30 fps  （Canvas）
LLM 建议              ●              ●       0.5 Hz  （1.5s 节流 + 变化触发）
```

用户感知上是"连续的实时引导"，实际算力消耗只有 1/3。**构图是慢变量——人在 100ms 内位移不到 5cm，不可能需要每帧重新检测。**

这个设计同时带来一个好处：**降级是渐进的**。手机发烫降频时，先掉到 6 fps 检测，跟踪接管补帧，用户几乎无感；而不是直接卡死。

### 5.1.1 ★ 流畅性：帧时间的确定性（2026-10-14 追加，本轮的验收基线）

> **背景**：用户澄清——他此前说的"**流程性**"实际是"**流畅性**"。
>
> 这是一个**方向性的纠正**。上一轮把它理解成"架构能否平滑演进"，答案是"接口先定"（§2.5）。但用户真正要的是**运行时不卡**。这是两件不同的事，后者必须用**帧时间统计**来验收，而不是架构图。

**一、流畅 = 帧时间的确定性，不是平均值**

| 不成立的说法        | 成立的说法                          |
| ------------- | ------------------------------ |
| "平均 30fps"    | "**P99 帧时间 ≤ 33.3ms**"         |
| "跑得挺快的"       | "**最大连续掉帧 ≤ 2 帧**"              |
| "帧率达标就行"      | "**1% 的最慢帧也不能超一帧预算**"          |

反例：每 2 秒卡顿 100ms、其余时间跑 60fps，**平均帧率仍接近甚至高于 30fps**，但用户感知是"一卡一卡"。**平均值会把这种体验完全掩盖。**

**二、验收指标（建议基线，见 §10.6）**

| 指标            | 目标                 | 说明                     |
| ------------- | ------------------ | ---------------------- |
| P99 帧时间       | ≤ **33.3ms**       | 1% 的最慢帧也不能超一帧预算        |
| P99.9 / max   | ≤ 2× 预算（66ms）      | 极端长尾                   |
| 掉帧率           | < **5%**           | 超过预算的帧占比               |
| 最大连续掉帧        | ≤ **2 帧**          | 连续掉 3 帧以上人眼明显感知        |
| 温升后帧率保持率（10min） | ≥ **70%**          | 抗降频                    |
| **GC / 热路径分配停顿** | **热路径 0 次分配**      | 见下——这是唯一能穿透保险的抖动源   |

**三、五类破坏源与本方案的已有对策**

| 破坏源           | 本方案对策                                        | 位置                 |
| ------------- | -------------------------------------------- | ------------------ |
| **跨语言帧拷贝抖动**  | 帧不进任何跨语言边界                                   | §2.1 / §3.8        |
| **推理长尾**（某帧特别慢） | 检测 10~15fps + 跟踪补帧 30fps                     | §5.1               |
| **GC / 内存分配抖动** | 热路径预分配 + 对象池                                 | §3.8               |
| **温升降频**      | 渐进降级 + 分辨率动态切换（640↔416）                      | §5.1 / §8.2        |
| **UI 线程阻塞**   | 取景器双端原生、叠加层独立 layer                          | §3.7.5-4 / §5.3    |

**四、⭐ 最关键的一条因果链**

`检测 10~15fps + 跟踪补帧 30fps` 这个设计的真正价值，**不只是省算力**——它是把**推理的长尾抖动**与**预览帧率**解耦：

> 检测偶尔慢 20ms，跟踪照常以 30fps 补帧，**预览层完全无感**。这是流畅性的**第一道保险**。

**而 GC 抖动是唯一会穿透这道保险的**——因为它发生在 native / 中间层的**每帧热路径**上，跟踪补帧本身也会被停顿卡住。所以：

- Phase 2 感知热路径**全在 C++（不分配）** → GC 影响不到
- 中间层（Kotlin `commonMain`）的**每帧路径若分配** → GC 停顿会周期性卡住整条流水线

> **→ 结论：Kotlin/Native GC 抖动从"可选闸门"升级为"流畅性的头号风险"。**
> 这正是本轮澄清带来的判断变化——上一轮我把它当作"可以并行测的备选项"，但在"流畅性"这个诉求下，它是**决定成败的单点**（见 §8.2 与 §10.3）。

**五、为什么这条澄清重要**

它把一条模糊的产品直觉（"要流畅"）变成了**可以在 M0 就开始采集、每个里程碑都可回归的量化基线**。从 M0 起，Debug 浮层就必须同时显示：**当前 FPS + 帧时间 P99 + 最近 60 帧的间隔条状图 + 最大连续掉帧**——见 §5.3。**没有这些数字，"流畅"就无法验收。**

### 5.2 本地规则引擎（LLM 的兜底，也先于 LLM 存在）

必须在接 LLM **之前**就有一套本地规则引擎，原因有三：离线可用、延迟更低、作为 LLM 输出的合理性校验。

规则示例（每条都是几何可验证的）：

| 规则    | 条件                                   | 输出提示              |
| ----- | ------------------------------------ | ----------------- |
| 脚底截断  | `person.boxBottom ≥ 0.98`            | "退后两步，把鞋拍进去"      |
| 头空间不足 | `boxTop < 0.06`                      | "抬高手机 / 退后，头顶要留白" |
| 主体过小  | `boxH/frameH < 0.35`                 | "走近些，或者用 2x"      |
| 偏离三分线 | 眼睛 y 偏离上三分线 > 8%                     | "手机往下压一点"         |
| 背景抢主体 | 背景区域饱和度高且与主体色相差 > 90°                | "往右边挪，避开后面那辆红车"   |
| 遮挡    | 前置主体脚底 y > 后方主体脚底 y                  | "往后站一点，别让她被挡"     |
| 主体贴边  | `boxLeft < 0.03` 或 `boxRight > 0.97` | "她快出画了，往左转"       |
| 水平倾斜  | 由地平线/建筑垂直线估计 roll > 2°               | "手机往右转一点，画面歪了"    |

> 这层逻辑写在 **Kotlin commonMain**——近原生速度、可单测、双端共享（§3.7.4）。
> **Phase 1 无感知层，规则引擎暂不生效**；但它可以在 Phase 1 就用"云端返回的 JSON"作为输入来跑，为 Phase 2 预热。

### 5.3 Debug 模式（你明确要求的轮廓标注）

设计成**编译期可剥离 + 运行期零开销**：

- 入口：长按提示卡 3 秒 → 调试面板；或 debug 构建时右下角常驻按钮
- 实现：Compose `Canvas` 叠在相机预览之上。**取景器 UI 走双端原生（§3.7.5-4）**：Android 用 Compose Canvas，iOS 用 Compose MP Canvas 或直接在原生取景器视图上叠一层。用 `Modifier.drawWithCache` / 预建 `Path` 对象，**不在每帧重建绘制对象**
- 坐标系：分析帧侧输出**已归一化**的框/关键点坐标，UI 侧只做 `归一化 → 预览视图尺寸` 的映射。旋转与裁切在相机层统一处理
- 绘制内容：
  - 所有检测框轮廓 + 类别 + 置信度
  - pose 关键点骨架连线（判断姿态识别是否准确）
  - 三分线 / 中心线 / 地平线参考线
  - 每个框的主色色块（验证颜色提取）
  - **性能浮层**：`cap 8ms | pre 4ms | det 42ms | pose 31ms | track 0.4ms | bridge 0.2ms | FPS 12.3`
  - ⭐ **流畅性浮层（§5.1.1 要求）**：`P99 41ms | 掉帧 3.2% | 最长连掉 1 帧 | 温升后保持率 —`
  - **降级指示**：条状图显示最近 60 帧检测间隔，降频立刻可见
- 关闭时：`if (!debug) return;`，**不构造任何绘制对象、不产生绘制指令**

> 注意：这是"预览层 + 独立叠加层"两层合成（不是同缓冲绘制）。好处是叠加层崩了/卡了不影响预览；代价是坐标系要自己对齐。**M1 阶段建议先做一个"坐标对齐可视化"小工具**，否则后面所有 UI 都会踩偏。

**这个 Debug 模式本身就是你验证"模型准不准"的唯一手段，属于 M1 的验收交付物，不是可选项。**

### 5.4 深度（层次）的取舍

YOLO26n-depth（768×768）CPU ONNX 延迟 **272 ms** — 直接在手机上跑是灾难。

所以用**三档策略**，默认最低档：

| 档位    | 方式                                                 | 成本                          | 何时用                   |
| ----- | -------------------------------------------------- | --------------------------- | --------------------- |
| A（默认） | 只用 `脚底 y 坐标` 排序                                    | ~0                          | 常规人像，机位大致水平           |
| B（按需） | 深度模型降分辨率到 256~320，**每 6~10 帧跑一次**，只在多主体重叠时启用       | 降采样后约 30~60ms，摊薄后 5~8ms/帧   | 检测到 2 个以上 person 且框重叠 |
| C（不开） | 高倾角 / 特殊场景提示"层次不可靠"                                | 0                           | 俯拍仰拍时明确标注置信度低         |

**原则：宁可说"我不确定"，不要输出错误的空间关系。**

## 6. 远端大模型接入

### 6.1 输入：按形态区分（Phase 1 传图 / Phase 2 默认不传图）

> 📌 **修订（配合 §2.3 与 §2.4）**：原设计"默认不传图"成立的前提是**实时取景、每秒都要决策**。**单图形态下这个前提反转**——详情见 §2.4.3。

**形态对照：**

| 形态                 | 默认输入策略                                  | 理由                            |
| ------------------ | --------------------------------------- | ----------------------------- |
| **Phase 1 单图**     | **传图**：缩略图 512px ＋ 主体裁剪图 ＋ 精简 JSON      | 只传一次，延迟可接受；"理解构图（审美）"**必须让模型看到画面** |
| **Phase 2 实时**     | **默认不传图**：仅精简 JSON（可选开"传缩略图"开关）          | 每秒都要决策，传图太贵太慢                 |

**Phase 2 的 JSON 结构（默认输入）：**

```jsonc
{
  "intent": {
    "mode": "portrait_half",           // L0 预设
    "user_text": "突出她的红裙子，背景要有海",  // L1 文字，可为 null
    "priority": ["subject_dominant", "background_sea"]
  },
  "frame": { "w": 720, "h": 1280, "orientation": "portrait" },
  "subjects": [{
    "id": 1, "cls": "person", "conf": 0.91,
    "box": [0.31, 0.22, 0.68, 0.96],   // 归一化 xyxy，不传像素不传图
    "height_ratio": 0.74,
    "center": [0.495, 0.59],
    "headroom": 0.22,
    "bottom_cut": false,
    "dominant_colors": ["#B3243A", "#1A1A1A"],   // 红裙 + 深色
    "pose_summary": { "shoulder_angle_deg": 12, "facing": "three_quarter_left", "arms": "down" },
    "depth_rank": 1                              // 层次：1=最前
  }],
  "background": [{
    "cls": "water", "coverage": 0.31, "dominant_colors": ["#4A6B7C"], "depth_rank": 3
  }],
  "composition": {
    "rule_of_thirds_offset": 0.061,      // 眼睛偏离上三分线的比例
    "horizon_roll_deg": -1.8,
    "subject_bg_contrast": 0.42,         // 色相差
    "clutter_score": 0.28                // 背景杂乱度
  },
  "device": { "tier": "mid", "fps_actual": 11.2 }
}
```

**为什么 Phase 2 默认不上传图像：**

1. 成本：视觉输入 token 是文本的数十倍，0.5Hz 调用下差距巨大
2. 延迟：多模态首字延迟通常 +300~800ms，本场景延迟是体验生死线
3. 隐私：**"给女友拍照"是强隐私场景，默认不上传画面是产品态度**
4. 可控性：JSON 里的数字可被本地校验，纯图像黑盒输出没法兜底

**Phase 2 提供一个可选开关**"允许上传缩略图（512px）提升理解力"，默认关闭，开启时明确告知。

### 6.2 输出契约

强制结构化，便于本地校验与渲染：

```jsonc
{
  "photographer_action": "后退一步，蹲下约 30cm",   // ≤ 15 字，你该做什么
  "model_script": "头往右转一点，看远处别看我",      // ≤ 20 字，直接照念
  "reason": "现在她偏右且头顶贴边，退后能同时解决两个问题",
  "confidence": 0.82,
  "priority": "high"
}
```

**约束：一次最多 2 条建议。** 提示超过 2 条，用户就不照做了——这是产品纪律，写进 prompt 也要在本地代码里二次裁剪。

### 6.3 触发与节流策略

| 触发条件     | 说明                              |
| -------- | ------------------------------- |
| **变化触发** | 几何特征向量与上次请求的 L2 距离 > 阈值（画面真的变了） |
| **最小节流** | 距上次请求 ≥ 1.5s（硬下限，防止抖动刷屏）        |
| **状态事件** | 主体入画/出画、人数变化、姿态大幅变化 → 立即触发      |
| **意图变更** | 用户改文字/换场景 → 立即触发                |
| **静止抑制** | 画面 1s 内几乎无变化 → 不请求（省成本，也避免重复建议） |

> **Phase 1 单图形态下不需要节流**——用户主动按快门才触发一次。

### 6.4 降级链路（必须实现）

```
LLM 正常           → 流式上屏，逐字显示
LLM 超时/5xx       → 重试 1 次（仍 1.5s 节流）
重试仍失败         → 切本地规则引擎，UI 标注「离线模式」
本地也无高置信规则 → 显示「画面 OK，保持住」，不硬编建议
网络恢复           → 自动切回，不打断当前提示直到该条展示完毕
```

**"绝不静默失败"——这是你的既有原则，我按同一标准设计：所有降级都必须有可见的状态标注。**

| **M4 调优**       | 模型微调（构图类目）+ 深度可选档 + **GC 抖动实测与调优** + **流畅性达标** + 功耗优化                                    | 连续使用 10 分钟无严重降频（掉帧 < 30%）；**§10.6 流畅性指标全部达标**            | M3   |
| **M5 打磨**       | 引导箭头 / 取景框 / 口播台词卡 / 参考图模仿                                                              | 用户测试采纳率 > 60%                                             | M4   |

> **KMP 路线的里程碑与 Flutter 路线结构相同，但 M1 的难度显著下降**：不需要"自研相机帧 FFI 通道"（§3.5 那个唯一的一级风险），KMP 里相机帧天然在 Kotlin 内流动。M1 的主要工作量转为 **NCNN 的 `extern "C"` shim + 双端绑定**（这是三方案共享的成本，不是 KMP 特有）。
>
> **M0 的相机层是两个平台各一个类**（Android CameraX / iOS AVCaptureSession），比 RN 的"零相机代码"多，但比 Flutter 的"自研插件 + Texture 注册"少。

**垂直切片原则不变**：先打穿一条窄而深的路——相机 → 帧 → 推理 → 轮廓 → 性能数字。**如果 M1/M1.5 的实测帧率不达标，退路见 §8.2**（换 NCNN 后端 / 降分辨率，或回退 RN）。

**实现顺序建议（§10.2）**：虽然是双端目标，但 **M0/M1 先在 Android 上打穿**，再照搬到 iOS——能早拿到真实性能数据，且避免同时踩两个平台的坑。**iOS 侧本机无法构建，见 §8.2。**

### 8.1 许可风险 —— **已解除（评审确认纯自用/不商业化）**

Ultralytics YOLO 全系（含 YOLO26）采用 **AGPL-3.0** 许可。AGPL 的传染性覆盖"通过网络提供服务"的场景。

**当前决策是"纯自用 / 不商业化"，因此 AGPL 不构成约束，可放心使用 YOLO26 检测 + pose + depth 全家桶。**

> ⚠️ **触发条件留档**：若将来转向商业化（上架收费、接广告、做 SaaS、对外提供服务），必须在发布前二选一：
>
> 1. 购买 Ultralytics 商业许可（Enterprise License，需询价）
> 2. 换用 **Apache-2.0 / MIT** 许可的模型：**RT-DETR**（PaddleDetection，Apache-2.0，但移动端部署难）、**YOLOX**（Apache-2.0，生态成熟）、**NanoDet-Plus / PicoDet**（Apache-2.0，极致轻量）
>
> 好消息：§4.4 已经把推理层设计成 **C++ + NCNN 的独立层**，换模型的成本主要是重新导出 + 改后处理，**不是重写架构**。这是自研 C++ 路线的一个额外红利。

### 8.2 其他风险

| 风险                                          | 影响               | 对策                                                          | 阶段    |
| ------------------------------------------- | ---------------- | ----------------------------------------------------------- | ----- |
| **★ Kotlin/Native GC 抖动**（**流畅性头号风险**，§5.1.1） | 热路径停顿 → 周期性卡顿、掉帧 | **热路径全用预分配缓冲 + 对象池**（§3.8 纪律）；用 PC 上 `mingwX64` 基准先量化；**P99 > 2×P50 则把更多热逻辑下沉 C++** | M1~M4 |
| **★ iOS 侧本机无法构建/实测**（无 macOS/Xcode）          | 双端目标中 iOS 半程无法验证  | 先用开源先例做代码可行性审查（klover / GalwayBus）；需要一台 Mac 才能彻底解决          | 全程    |
| **手机发烫降频**                                  | 连续推理 10 分钟后帧率腰斩  | 自适应降频（§5.1 渐进降级）；检测分辨率动态切换 640↔416；提供"省电模式"；**§10.6 温升保持率 ≥70% 作为验收** | M4    |

| 推理算子回退（NCNN 不支持某算子）                         | 性能静默暴跌           | Debug 浮层显示实际后端与分段耗时；保留 TFLite / ONNX Runtime 双备份路径          | M1.5  |
| **cinterop 只能调 C ABI，NCNN 是 C++ 类**           | 编译不过（硬前置）        | **先写 `extern "C"` 薄 shim**——必须列进 M1，不能等到写推理时才发现             | M1    |
| **Compose MP 取景器掉帧**（英雄界面）                    | 预览不丝滑            | 取景器 UI **双端原生**（§3.7.5-4），只共享逻辑与相机层                         | M0    |
| Kotlin/Native 编译慢                             | 迭代节奏慢            | 逻辑层放 `commonMain` 尽量复用；Android 侧全程 JVM 编译快，日常调参在 Android 上做 | 全程    |
| 坐标对齐错误（预览 vs 帧坐标系）                           | Debug 轮廓画偏，误导判断  | 分析帧侧输出已归一化+已校正方向的坐标；M1.5 先做对齐可视化工具                          | M1.5  |
| 单人姿态在侧身/背影时关键点不准                             | 误判朝向             | 置信度低于阈值时不输出朝向相关建议                                           | M2    |
| LLM 输出幻觉（建议与画面矛盾）                            | 用户信任崩塌           | 本地规则校验 LLM 输出：与几何特征冲突的建议直接丢弃                                | M3    |
| 弱网/高延迟（>5s）                                  | 建议到达时画面已变        | 延迟 > 3s 的建议丢弃不上屏，宁可不说                                       | M3    |

**若 M1 帧通路实测不达标，两条备选路径（按优先级）：**

1. 换推理后端（NCNN → TFLite / ONNX Runtime）或降低检测分辨率/频率（640→416，检测 10fps→6fps）
2. **回到 React Native 方案**（§3.2 的原始推荐，相机层由 VisionCamera 直接提供，帧通路开销实测仅 ~1ms）

**分两处放逻辑是有意为之**：

- **`commonMain`（Kotlin）** 放**要反复调参**的层——跟踪、特征、规则。近原生速度 + **可单测** + 双端共享，这是 KMP 相对 Flutter 的核心收益（§3.7.4）。
- **`shared-native`（C++）** 只放**稳定且纯计算**的层——NCNN facade、预处理、后处理。它们变更少，且能跨方案复用（§3.7.5-1）。

**`tools/eval/` 的价值在 KMP 下稍低于 Flutter 路线**（因为跟踪/特征层是 Kotlin，可直接单测），但仍值得建：它能在 PC 上跑完整链路，验证 LLM prompt 与规则引擎的端到端效果，不用每次真机。建议 M2 阶段建起来。

| 输入 | 支持 base64 内联 / 外链 URL / Files API 引用（兼容 OpenAI Chat Completions） |
| 图片计费 | 按尺寸折 token，**单张最多 384 token** |
| 费率 | 输入 ¥1 / 输出 ¥2 每百万 token |
| 下采样 | `detail: "low"` → 服务端降到 **512×512** 再推理 |

**意义**：§2.2.6 路线 A（单图直传云端 VLM）不再需要任何折衷——
不需要本地压缩、不需要裁剪上传。`detail:"low"` 恰好就是 §2.4.3 三件套里
「缩略图 512px」那一件，服务端替我们做了。

> ⚠️ 保留：官方标注实验性质，模型名与口径可能变 → 因此**模型名做成可编辑字段**，不写死。

### 11.2 远端大模型：可配置是怎么做的

```
LlmConfig（持久化到 SharedPreferences / NSUserDefaults）
  providerId / baseUrl / model / apiKey
  sendImage / lowDetail / temperature / maxTokens / timeoutMs / extraInstruction
```

换服务商**不改代码**：通义 / 豆包 / 自建 vLLM / One-API 网关只要兼容 `/chat/completions`，
改 `baseUrl` + `model` 两个字段即可。

**为什么不用厂商原生 SDK**：一旦引入，就等于把"可配置"这件事交出去了。
2026 年 OpenAI 兼容格式已是事实标准，自己维护 HTTP + JSON 这一层成本极低。
